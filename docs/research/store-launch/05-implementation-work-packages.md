# حزم التنفيذ وتسليم العمل

المصدر الآلي للمهام: [launch-plan.json](launch-plan.json). كل مهمة تحتوي priority وdependencies وtarget paths وacceptance وeffort وsource refs وgate. الحالات الحالية تخطيطية؛ لا مهام منجزة بمجرد كتابة هذه الحزمة.

## ترتيب التنفيذ

| المرحلة | المهام | المخرج الملزم | ما يمنع الانتقال |
| --- | --- | --- | --- |
| G0 تحديد النطاق والحقوق | 001–002 | سجل قرارات وأصول | مالك/حقوق موسيقى/خط غير محسومة |

الأرقام هي آخر ثلاث خانات من `YKL-xxx`. اختيار online يؤثر في conditional tasks فقط؛ لا يجوز إسقاطها دون قرار نطاق مسجل وإزالة الوعد من المنتج وكل مواد المتجر. المسار البديل native له مهام منفصلة، ولا تجمع تقدير المسارين كأنهما كلاهما مطلوبان.

## نقاط تسليم دقيقة

### YKL-003 / YKL-004 — التجربة والقرار

من المدخلات الحالية اصنع لاحقًا build تجريبيًا داخليًا، لا إصدار متجر. قِس لا تفترض. حفظ تقرير يتضمن Godot وexport templates وCapacitor والplugins وXcode/SDK وAndroid toolchain؛ استخرج أقل OS فعلي من الحزمة. اختر toolchain مستقرة ومثبتة. تحديث Godot4.7.1 إلى4.7.2 مقترح تقييم بعد مراجعة release notes [S42]، وليس شرطًا ولا ترقية منفذة.

تقرير القرار يجيب: هل package يعرض اللعبة دون اتصال؟ هل تعمل crypto/WebRTC بالـorigin المحلي؟ هل ينجح الصوت والكيبورد؟ ما peak memory ومدة البدء؟ هل ظلت الطاولة والموشن معتمدة؟ هل يمكن إصلاح الإخفاقات في 3–5 أيام أم ننتقل؟

### YKL-005 / YKL-006 / YKL-029 — حدود الواجهة

لا تمس قواعد الفوز. اجعل source-of-truth configuration نفسه ينتقل إلى اللعب. ابدأ بتجريد lifecycle وstorage وinvitation حول UI الحالية إذا اختير wrapper. عند native أعِد تقديم **نفس** أوامر `preview/start/join/learn/learn-next/learn-close` في Control أو adapter مكافئ؛ لا تترك callbacks DOM صامتة. تبقى سلطة المشهد للكاميرا والمجسمات، ولا تعيد كل widget بناء الطاولة.

### YKL-007 / YKL-008 — الهوية والتخزين

توصية ضيف بلا هاتف تستلزم قرارًا واضحًا ثم تعديل validation ودخول الواجهة والاختبارات المتأثرة. في wrapper، ملفات Safari لا تظهر تلقائيًا في WebView؛ لا تعد المستخدم بنقل اسم المتصفح إلى التطبيق. راع versioned storage وclear local data والكتم واختيار تقليل الحركة. عند native استخدم `user://` ولا تضع سرًا طويل الأمد في settings نصية إن دخل النطاق.

### YKL-009 — release والتشخيص

احصر `yakolakTestFast` وfixtures وbrowser automation والتشخيص. نفّذ سياسة معلنة واحدة في release؛ لا reviewer detection ولا تعطيل وظيفة لمراجع. قارن نفس fixture في release/debug في قواعد اللعب والاختيارات. تحقق من عدم محاولة `/api/telemetry` أو `/api/rooms-observed` التاريخية في نسخة الإنتاج المختارة. لا تحذف وحدات القواعد المستوردة من `api/`.

### YKL-010 / YKL-011 / YKL-012 — الجودة الجوهرية

أعد استخدام `scene_motion.gd` وتسلسل generations؛ pause لا يترك callback قديمًا يخفي حجرًا. عالج تغيير اتجاه الشاشة من وضع الكاميرا الحالي. قم باختبارات القفل/المكالمة/audio focus والرجوع وprocess death، ووضح نهاية غرفة المضيف. اختبر بدل افتراض أن setInterval يستمر في background. الجودة التكيفية تخفض resolution/ظلال/MSAA تدريجيًا أو عند نقطة آمنة دون قفز منظور أو اختفاء أحجار؛ لا تغيّر أوقات اللعب المعتمدة لتخفي بطء المحرك.

### YKL-014 / YKL-015 / YKL-030 — الاتصال

حافظ على تحولات القواعد نفسها، binding للمقعد، `epoch`، pending mutation والمهلة. الجسر الحالي يحرس Web صراحة؛ native يحتاج تنفيذًا جديدًا. إذا اختيرت خدمة جديدة، تضاف migration/protocol version ومتوافقات الويب بوضوح؛ لا تعد P2P القديم قادرًا على الحديث مع WSS جديد تلقائيًا. خادم/TURN/رسوم قرار لاحق وليست مشتريات مأذونة بالبحث.

### YKL-019 / YKL-020 / YKL-031 / YKL-032 — البناء

لكل binary: commit المصدر، hash للأصول، نسخة الأدوات، build number، Bundle/Package ID ثابت، مفاتيح خارج git، digest للملف، manifests، قائمة الأذونات، دليل التثبيت من قناة المتجر. لا يكفي sideload debug. لا تسجل أسرارًا/keystore داخل مستودع عام. قوالب أوامر البناء موجودة بالدليل التشغيلي ولا تعمل قبل تجهيز المسار.

### YKL-021 إلى YKL-026 — الإغلاق قبل الرفع

لا تكتب store screenshots أولًا ثم تغير التجربة. حسم الجمهور والخصوصية والربحية والتوزيع يسبق المحتوى. اجمع أدلة الاختبار لكل رقم build، حضّر ملاحظات reviewer، افحص الروابط كزائر، وأعد مراجعة السياسات الحية في يوم التقديم. إن تغير SDK أو plugin بعد القبول، أعد فحص الحزمة والسيناريوهات المتأثرة.

## قالب تكليف الوكيل المنفذ لاحقًا

```text
اقرأ AGENTS.md ثم docs/research/store-launch/README.md وlaunch-plan.json.
المطلوب تنفيذ task IDs المحددة في التكليف فقط بعد تثبيت قرار المسار والنطاق.
ابدأ من أحدث main؛ لا تنشئ branch أو PR ما لم يطلب المالك.
أعد فحص الأدلة القديمة على source SHA الجديد. حافظ على القواعد والموشن والواجهة المعتمدة.
لا تحول planned أو not_run إلى passed دون اختبار وأثر قابل للمراجعة.
سجل paths المتغيرة، سبب التغيير، وbuild/evidence/risks، ثم توقف عند بوابة القرار المطلوبة.
لا تفتح حسابًا مدفوعًا أو تنشر متجرًا أو تشتري خدمة لمجرد وجودها في الخطة.
```

## متى تكون الخطة قابلة للتنفيذ؟

بعد اختيار المسار ونطاق online والجمهور والهوية والحقوق، كل dependency له مخرج معروف، وكل acceptance يقبل نجاحًا/فشلًا بدليل. التقدير يُعاد بعد G1؛ الخطة الحالية لا تفترض أن ضغطة export تنجز الجوال ولا تخفي إعادة كتابة JS داخل بند صغير.
