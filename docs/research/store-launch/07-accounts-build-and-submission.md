# من المشروع إلى المتجر: دليل المالك والمنفذ

كل الإجراءات هنا مستقبلية؛ لا حساب أُنشئ ولا فاتورة دُفعت ولا binary رُفع أثناء البحث.

## المصطلحات الضرورية

| المصطلح | معناه في العمل |
| --- | --- |
| Apple Developer Program | عضوية تسمح بالتوقيع والتوزيع؛ ليست هي صفحة منتج اللعبة |
| App Store Connect | لوحة بيانات اللعبة والنسخ وTestFlight والمراجعة |
| Google Play Console | لوحة التطبيق والتجارب وبيانات السلامة والتوزيع |
| Bundle ID / Package name | هوية تقنية ثابتة للتطبيق؛ الاسم الظاهر للمستخدم مختلف |
| Build number / versionCode | رقم يزداد لكل binary؛ لا تعِد استخدام رقم مرفوع |
| IPA / archive | مخرج iOS مرتبط بـXcode والتوقيع؛ لا ينتجه Web export |
| AAB | حزمة Android المطلوبة للتقديم؛ Google يولد منها ما يلزم الأجهزة |
| Signing / upload key | إثبات صاحب الإصدار؛ لا يوضع داخل git ولا يرسل في دليل عام |
| TestFlight / closed test | توزيع تجريبي حقيقي قبل الإنتاج، لا بديل عن قرار المراجعة |

## 1. قرارات المالك قبل شراء شيء

املأ سجلًا خاصًا: من سيملك حسابَي النشر؟ فرد باسمه القانوني أم كيان فعلي؟ هل يريد ظهور الاسم الشخصي كـseller على Apple؟ هل الجمهور يشمل أطفالًا؟ هل النسخة مجانية أم مدفوعة؟ هل online ضمن أول إصدار؟ من يملك الموسيقى والتصميم والخط؟ هل يتوفر Mac وآيفون وأندرويد ومختبرون؟

لا تستخدم بيانات أو معرف نطاق مخترع. `sa.yakolak.webrtc.v1` في الكود namespace لخدمة الاكتشاف، وليس دليل ملكية دومين أو Bundle ID محجوز. لا تضع `com.example` في الإنتاج. يسجل المالك المعرفين النهائيين مرة واحدة ويتحقق من إمكانية استخدامهما.

## 2. حساب Apple

بحسب المصدر الرسمي [S27]: العضوية 99 دولارًا سنويًا مع تسعير محلي قد يختلف. الفرد يحتاج الاسم القانوني وتفعيل المصادقة الثنائية، ويظهر اسمه seller. المنظمة تحتاج كيانًا فعليًا وصلاحية تمثيله، وعادة D-U-N-S وموقعًا ووسيلة اتصال. اختيار منظمة ليس شرط قبول لعبة عادية.

مسار العمل: إنشاء/التحقق من الحساب → قبول الاتفاقات → تسجيل App ID → إضافة app record في Connect → ربط فريق التوقيع → أدوار المطور/المالك بأقل صلاحية لازمة. المدفوعات والضرائب والبنك تتفعل حسب نموذج البيع؛ لا نملأها افتراضيًا على أنها مكتملة.

**العتاد:** مسار Godot الأصلي إلى Xcode يحتاج macOS وXcode [S29]. wrapper iOS يحتاج أدوات Apple أيضًا. جهاز Windows أو Android VM لا يستبدل بناء وتوقيع iOS؛ يمكنه تجهيز المصدر وأندرويد، ثم يستخدم الفريق Mac فعليًا/مورد بناء Mac مصرحًا. لا تعتمد virtual iOS كاختبار جهاز فعلي.

## 3. حساب Google

بحسب [S28]: التسجيل 25 دولارًا مرة واحدة، مع تحقق هوية، واختيار فرد/منظمة. الحسابات الشخصية الجديدة المشمولة تحتاج كذلك إثبات الوصول لجهاز Android ومرحلة الاختبار. لا نفترض نوع حساب المستخدم أو تاريخه.

إذا كان الحساب الشخصي منشأ بعد 13 نوفمبر 2023، تحقق من شاشة المتطلبات: 12 مختبرًا منضمين بشكل مستمر 14 يومًا قبل طلب production access؛ ويبقون مستوفين عند الطلب. النتيجة تمر بمراجعة جودة الاختبار، ولا تمنحها أرقام الأيام وحدها [S13]. يوصى بتجنيد16–20 مستخدمًا حقيقيًا لتجنب فقد الحد الأدنى؛ هذا احتياط للمشروع وليس رقمًا تفرضه Google.

أنشئ app record كـGame وباللغة الرئيسية الصحيحة، وثبت package name والبلدان. فعّل Play App Signing، واحفظ upload key ونسخه الاحتياطية بطريقة منفصلة [S49]. لا تخلط debug keystore بمفتاح release.

## 4. تجهيز أدوات البناء

| البند | المطلوب لاحقًا |
| --- | --- |
| المحرك | pin للمحرر وexport templates بالإصدار نفسه؛ baseline4.7.1، وتقييم4.7.2 اختياري |
| wrapper إن اختير | نسخ مثبتة لـCapacitor/CLI/plugins وlockfile، أصول محلية في staging، دون remote live reload |
| iOS | Xcode مستقر يفي بحد26/SDK26 الحالي أو أحدث، فريق/Bundle ID/signing وأيقونات |
| Android | JDK17 مناسب لإرشاد Godot4.7، Android SDK/Build tools/NDK وGradle متوافقة مع engine والمسار |
| أقل iOS فعلي | لا يقل عن13 بسياسة Apple الحالية، وقد يكون أعلى بسبب Godot/renderer والأجهزة المقبولة؛ لا تساويه تلقائيا بـSDK26 [S51] |
| سياسة target | تثبيت platform/compile/target المتوافق مع API36؛ لا تنسخ SDK35 من المثال القديم دون تعديل |
| الأسرار | متغيرات/مخزن أسرار للـCI، لا source أو console output أو docs |
| البناء | release قابل لإعادة البناء مع قائمة إصدارات وبصمات، لا build debug مع اختبارات مخفية |

**أوامر مرجعية مستقبلية للمسار الأصلي فقط**؛ أسماء presets التالية غير موجودة حاليًا ولا تعمل قبل تنفيذ مهامها:

```bash
godot --headless --path . --export-release Android build/android/yakolak.aab
```

لتصدير iOS، يبدأ المنفذ بمسار Project → Export → iOS في إصدار Godot المثبت ويتحقق من مشروع Xcode الناتج. يثبت صيغة استدعاء CLI بعد تجربة exporter نفسه؛ لا نخمن امتداد ملف الإدخال للأتمتة من اسم مجلد Xcode النهائي.

أوامر wrapper تكون من حزمة Capacitor المثبتة محليًا بعد إعدادها: build/stage ثم sync، ثم البناء الأصلي عبر Xcode/Gradle. لا تستخدم ناتج `web/` غير معروف المصدر ولا تغيّر Workflow Pages ليتحول إلى نشر متجر تلقائي. أي workflows جديدة للمتجر يجب أن تكون صريحة ومعطلة عن الرفع الإنتاجي حتى طلبه.

## 5. حزمة التسليم الفنية

مطلوب لكل منصة: source SHA، نسخة engine/templates/toolchain، package ID، version/build number، تاريخ وhash للـbinary، license inventory، permissions/entitlements، privacy manifest عند اللزوم، تقرير startup/أجهزة/شبكات، ونتائج قبول بنفس build. لا تقارن نتائج simulator بملف متجر مختلف.

Android: افحص AAB عبر Play testing، ARM64 وكل `.so` للـ16KB وAPK الناتج؛ تغيير flag في `export_presets.cfg` لا يعيد بناء plugin غير متوافق. iOS: افحص archive النهائي وPrivacy report والتحذيرات والتشفير وأقل deployment target؛ لا تنسخ قيمة exemption من مشروع آخر [S10، S15].

## 6. مواد المتجر

| المادة | المطلوب | حالة هذه الجولة |
| --- | --- | --- |
| الاسم | «ياكلك»/Yakolak مع تحقق الحقوق والتوافر | مسودة |
| الوصف | قواعد وفائدة اللعبة بصدق، offline/bots/online بحسب النسخة | قوالب منفصلة للنطاق |
| اللغات | اذكر UI التي نُفذت واختبرت؛ وصف إنجليزي لا يعني واجهة إنجليزية | غير محسوم |
| الأيقونة | Apple ضمن asset catalog بمواصفاته، وGoogle512×512 للمتجر [S25، S46] | لم تُنتج |
| الصورة الترويجية | Google1024×500 وفق المصدر الحالي [S25] | لم تُنتج |
| screenshots | من build النهائي: لعب/ألوان/فوز/شرح؛ لا صور intro وحدها | لم تُلتقط |
| screenshots Apple | مثال مقبول1320×2868 للشاشة الكبيرة؛ راجع الجدول الحي والأجهزة المعلنة [S11] | ليست مقاسات لكل جهاز |
| الفيديو | اختياري؛ تسجيل فعلي للنسخة مع قصة قصيرة مفهومة | مؤجل |
| الخصوصية/الدعم | URLs عامة حقيقية ومن داخل التطبيق؛ بيانات التواصل بمالكها | placeholders فقط |
| الأعمار/المحتوى | استبيانات واقعية وتوثيق الناتج | لم تُعبأ |
| App access | خطوات محلي/بوت/شرح، واختبار online قابل لإعادة الإنشاء | قالب مراجعة |

لا تسوّق كلغات متعددة أو لعبة إنترنت مستقرة قبل قبولها. لا تذكر منافسًا أو «الأفضل/رقم1» أو جوائز وهمية. قوالب الوصف في `templates/store-listing.json` لا تُرفع آليًا.

## 7. التقديم خطوة بخطوة

**Apple:** رفع archive إلى Connect → انتظار المعالجة → إدخاله في TestFlight وإكمال اختباراته → اختيار build المرشح → metadata والخصوصية والتصنيف والتشفير → App Review Information بمعلومات تواصل وخطوات فحص → طلب review → قراءة أي أسئلة والرد عليها → اختيار إصدار يدوي عند القبول. فترة TestFlight وحدها لا تحقق إنتاجًا مقبولًا [S09، S02].

**Google:** رفع release AAB إلى internal testing → التثبيت من Play وتدقيق المحتوى والخصوصية والأذونات → closed test عند انطباقه → سجل feedback وإصلاحات → طلب production access مع وصف الاختبار → انتظار نتيجته → تقديم إصدار الإنتاج وبياناته للمراجعة. صلاحية production access ومراجعة binary/سياسات المحتوى مرحلتان مختلفتان [S13، S23].

لا تعتمد رمز غرفة موقتًا مكتوبًا في الملاحظات: قد يتأخر الفحص أيامًا ويختفي مضيفه. أعط خطوات إنشاء غرفة جديدة على جهازين، ومسارًا محليًا حقيقيًا كاملًا على جهاز واحد؛ وإن تعذر فحص جزء خاص، نسق مع فريق المراجعة ولا تخف الجزء.

## 8. بعد إرسال النسخة

احفظ حالة الإرسال ومراسلاته ورقم build. إذا وقع رفض، اتبع [دليل الاستجابة](08-rejection-cases-and-response.md) وأصلح سببًا ملموسًا، ولا تعِد الإرسال المتكرر دون تغيير مفهوم. لا تحجز إعلان إطلاق نهائي قبل الموافقة الفعلية. لا تعتبر نجاح Pages أو upload أو processing أو TestFlight موافقة App Store/Play Production.
