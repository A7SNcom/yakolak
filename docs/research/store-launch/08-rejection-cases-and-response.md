# الرفض الحديث: أدلة المطورين والاستجابة

نفرق بين **نص سياسة رسمي** و**شكوى مطور مباشرة** و**تفسيره للسبب**. الحالات ليست عينة إحصائية؛ لا تثبت معدل رفض أو ضمان طريقة للتحايل على المراجعة. المصادر الكاملة ورؤوس الثقة في `sources.json`.

## ماذا تؤكد البيانات الرسمية الحديثة؟

نشرت Apple في20 مايو2026 عن عام2025: أكثر من9.1 مليون submission تمت مراجعتها، وأكثر من2 مليون رُفضت؛ منها أكثر من443 ألف لأسباب خصوصية، وأكثر من371 ألف spam/تقليد/تضليل، وأكثر من22 ألف ميزات مخفية أو غير موثقة [S41]. هذه **طلبات إرسال بما فيها تحديثات وإعادات**، وليست عدد ألعاب جديدة فريدة أو نسبة احتمالية رفض ياكلك. لا يوجد في بحثنا إحصاء Google مماثل موثوق لتوزيع أسباب رفض الألعاب في2026.

## ترتيب المخاطر لهذا المشروع

| الخطر | دليل المشروع | الوقاية التنفيذية |
| --- | --- | --- |
| عدم اكتمال/تعطل2.1 | لا binary، UI web-only، قبول أجهزة ناقص | G1/G2/G4، clean install ولعبة كاملة |
| خصوصية متناقضة | هاتف محلي + اسم P2P + تشخيص اختياري + relays | data map من build وتوثيق الشركاء، لا عبارة blanket «لا بيانات» |
| وظيفة محدودة4.2 | لو رفع intro/رابط فقط | كل آليات اللعب والشرح والبوتات متاحة فعليًا دون موقع بعيد |
| حقوق/أصالة4.1/4.3 | أصول غير موثقة، تشابه صنف ألعاب معروف | سجل الحقوق وفيديو تجربة أصلية وأسماء وأيقونات تخص المشروع |
| UGC/تصنيف | أسماء حرة عبر رمز سهل التخمين | اختيار أحد مساري السلامة قبل الإعلان عن online |
| إخفاء سلوك | diagnostics/fixtures/flags ضمن المصدر | release واضح، لا detection للمراجع ولا تغيير خفي بعد القبول |
| طلب اختبار إضافيGoogle | نوع الحساب والمختبرون مجهولان | تحقق الحساب وتجنيد حقيقي وسجل من اليوم الأول |
| رفض رفع تقني | target/toolchain/16KB/التوقيع مجهولة | استخراج manifests وفحص native libraries وتوزيع testing |

هذا ترتيب عمل بحسب الأثر وغياب الدليل، وليس توقعًا بصدور بنود الرفض نفسها.

## بروتوكول الرد

1. احفظ النص كاملًا، guideline، الجهاز/OS، screenshot، submission/build، وتوقيت الرفض. فرّق rejection عن waiting وinformation needed وproduction access.
2. أعد السيناريو على الحزمة المرسلة ونفس المنصة قدر الإمكان. اطلب تفاصيل محددة إن كانت ناقصة؛ لا تتهم المراجع أو تفترض نظام كشف binary.
3. سجل root cause المؤكد أو الفرضية بوضوح، وغير أضيق جزء يحل المشكلة مع اختبار رجعي مناسب.
4. أرسل build جديدًا إذا تغير binary، أو عدل metadata إذا كانت هي السبب، مع خطوات ولقطة/فيديو قصير. لا تقل «أصلحنا» بلا دليل.
5. إذا كان سوء فهم، اشرح القيمة وسلوك التطبيق وأرفق دليلًا، واستخدم قناة appeal وفق تعليماتها؛ Apple تطلب تفسيرًا محددًا واستئنافًا واحدًا لكل submission [S02، S44].
6. راجع حالات مماثلة كمؤشرات فقط. لا تعطّل الميزة للمراجع أو تبدل remote configuration بعد قبوله لتجاوز القرار.

## قوالب رد قصيرة — تملأ من نتيجة حقيقية

```text
Thank you. We reproduced [issue] on [device / OS] in build [old].
The cause was [confirmed cause]. Build [new] changes [specific behavior].
Verification: [steps and evidence]. The feature is available to all users.
Review steps: [short sequence].
```

```text
Thank you. We would appreciate clarification about [specific missing detail].
The attached recording shows [actual feature] in build [number].
To reach it: [steps]. Please share the review device / OS and observed result
if the behavior differs. No reviewer-specific behavior is enabled.
```

لا ترسل العبارة الأخيرة إلا بعد تدقيق release؛ هذه مسودات داخل المشروع وليست مراسلات أُرسلت لأي جهة.
